# 本地 AI 古籍候选工厂设计

日期：2026-08-26  
状态：已确认  
模型：`deepseek-v4-flash`  
单次运行预算上限：人民币 20 元

## 背景与问题

现有推荐池共 461 个名字，其中 25 个经过人工核验，另外 436 个主要由古籍正文中的相邻双字和少量字符规则生成。这个方法能够扩大覆盖面，却无法可靠判断两个字组合后是否像真实姓名、整体语义是否成立，以及与姓氏“王”连读是否悦耳。结果中存在“随机摘字感”、语义残片、偏男性化和完整姓名拗口等问题。

新方案不废弃现有古籍全文库、段落索引和搜索能力，而是在它们与网页推荐池之间加入一个只在本地运行的候选工厂。工厂使用语言模型做生成和分角色审核，本地确定性程序负责证据、字形、读音、重复和预算校验。GitHub Pages 仍然只部署静态候选数据，不在浏览器中调用模型，也不包含 API Key。

## 目标

- 从现有古籍全文中生成语义完整、音韵自然、适合王姓女孩的双字名。
- 保留不连续取字、首尾取字、尾首衔接、对偶和篇内意象重组等传统取名路径，不局限于原文连续双字。
- 把“典籍证据”“姓名质量”“个人适配”和“传统参考”分开保存及展示。
- 第一轮发布约 300–500 个高质量候选；后续根据用户反馈继续扩充，而非一次堆积大量低质量组合。
- 单次完整运行的估算费用不得超过人民币 20 元，并能断点续跑。

## 非目标

- 不在 GitHub Pages 或浏览器端保存、代理或调用 DeepSeek API Key。
- 不让模型自行断言某句古文存在；出处必须由本地语料验证。
- 不在孩子实际出生信息确定前，把八字推断作为候选硬门槛。
- 第一版不训练或微调专用模型，也不使用 DPO；浏览器端继续采用现有可解释偏好模型和 MMR。
- 不追求发布尽可能多的名字。未通过审核的组合可保留在全文搜索中，但不进入推荐信息流。

## 总体架构

在现有前端 TypeScript 包中新增独立工具目录 `web/factory/`，从仓库根目录通过 `pnpm --dir web factory:build` 运行。这样复用同一份 Node 版本、锁文件与测试工具，但工厂仍只在本机执行：

```text
现有古籍全文与段落索引
  → 检索可取名语句与意象片段
  → DeepSeek 候选生成器
  → 本地确定性规则闸门
  → DeepSeek 匿名语义审查
  → DeepSeek 姓名感与音形审查
  → DeepSeek 对抗复审
  → 本地证据回查、去重与分层
  → 静态候选 JSON
  → 现有偏好学习 + MMR 信息流
```

同一个模型承担多个角色，但每个角色使用独立提示词、独立请求和独立缓存，后续审查器看不到生成器给出的自评分。模型统一使用官方标识 `deepseek-v4-flash`。批量生成采用较高多样性，审核采用低随机性；只有最终对抗复审在必要时使用更强推理模式。

## 候选来源与生成策略

工厂先从现有语料选出含有正向或中性意象、上下文足够完整的句段，再把原文和结构化元数据交给生成器。每个批次要求覆盖不同朝代、文体、作者和意象，防止候选集中在“玉、影、清、月”等少数字上。

生成器可提出以下来源类型：

- `exact-phrase`：原文中连续出现且本身语义完整；
- `clause-related`：同句的对偶、并列、修饰或首尾取字；
- `passage-related`：同段或同篇内语义一致的意象重组；
- `cultural-recomposition`：来源透明的跨句或家族意象重组。

每个提案必须给出两个名字用字各自对应的原文位置、组合释义以及为什么适合作为女孩姓名。生成器的解释只是待审查材料，不能直接作为网页事实。

为保持候选多样性，批次按典籍、风格、常见度和取字方式分桶，并限制同一汉字、同一原句和同一意象的产出量。家族字“玉”“影”“绍”作为可选的文化线索和少量专门批次，不再对全局候选固定加分，也不占据主体比例。“王令仪”和“王景玉”作为已知审美锚点，用于描述偏好边界，不要求生成相似字面组合。

## 分角色审核

### 1. 本地规则闸门

在调用后续审核前先执行低成本检查：规范汉字、禁用虚词与专名残片、重复、来源段落存在性、原文定位、明显负面上下文、王姓连读的基础谐音、多音字和书写风险。硬规则失败的候选不能被模型高分覆盖。

### 2. 匿名语义审查

审查器只看到候选、原文上下文和取字声明，不看到生成器的评价。它判断两字组合是否形成完整且自然的意义、解释是否忠于原典、取字关系是否被夸大，并返回通过、待人工复核或淘汰及可核查理由。

### 3. 姓名感与音形审查

审查完整姓名“王××”，分别判断声调节奏、声母韵母碰撞、常见误读、谐音、字形重心、女性气质、时代感、随机拼字感和日常称呼自然度。评分以分项数据保存，不合成为不可解释的文化总分。

### 4. 对抗复审

对高分候选使用反方视角寻找问题，重点回答“为什么它可能难听、牵强、像网名、像男性名、像生造词或难以长期使用”。只有对抗审查后仍成立的候选进入发布池。

## 数据结构与产物

每个发布候选至少包含：

- 姓名、双字名、拼音、声调和多音字风险；
- 典籍、作者、篇名、原句、上下文、语料定位和取字方式；
- 整体释义、典故说明和家族关联（如有）；
- 古典感、端雅、柔和、明净、清峻、现代感、易读、易写、易认、少见度等特征；
- 音韵、姓名感、语义、典故可信度和风险分项；
- 审核状态、审核理由、模型、提示词版本、语料版本和生成批次。

一次运行产生三类文件：

1. `web/corpus/generated/approved-candidates.json`：经审核、可提交并由语料构建器导入的源候选；
2. `web/public/data/generated-candidates.json`：本地预览及构建后的静态候选副本；
3. `web/factory/reports/<run-id>/review-report.json` 与 `manifest.json`：通过、待复核、淘汰、模型版本、请求数、token 和估算费用。

模型结构化响应缓存放在 `web/.factory-cache/`，检查点与完整报告只留在本地并加入 `.gitignore`。网页发布文件不得包含提示词、API 原始响应或任何凭据。

## 网页接入与偏好闭环

候选工厂只负责候选质量，不替代现有的个性化推荐。网页加载新的已审核候选后，继续使用浏览器本地反馈学习与 MMR：用户对单个名字选择“很喜欢、还不错、不喜欢、跳过”，系统更新风格偏好；推荐层以个人适配为主，同时限制共享汉字、近音、同典籍和同意象的连续曝光。

新候选通过稳定的姓名 ID 与现有收藏、排除、比较和反馈记录关联。重新构建候选库时，仍存在的名字保留历史反馈；被撤下的名字不再推荐，但用户收藏记录不被静默删除。当前 436 个规则粗筛候选默认降为 `search-only`，只有重新通过新工厂审核者才能回到推荐池。25 个已人工核验候选也进入统一数据结构，但保留人工核验标记。

## API Key 与安全

DeepSeek Key 只从本机环境变量 `DEEPSEEK_API_KEY` 读取。仓库提供不含真实值的 `.env.example`，开发者可在被 `.gitignore` 排除的 `.env.local` 中配置新 Key。程序不得在终端、报告、缓存键、异常文本或调试日志中输出 Key，请求错误保存前必须脱敏。

已经在聊天中暴露的 Key 视为不安全，不写入任何文件，也不用于测试；运行前应在 DeepSeek 控制台撤销并新建。真实 API 测试必须显式开启，默认测试套件全部使用模拟响应。

## 预算控制

单次完整运行采用人民币 20 元硬上限，内部预算分配如下：

- 2 元：小批量试生成和提示词校准；
- 10 元：多来源批量生成；
- 5 元：语义、音韵、女性气质和姓名感交叉审核；
- 2 元：高分候选对抗复审；
- 1 元：失败重试和机动余量。

费用控制器根据官方单价配置、返回的 token 使用量和显式汇率参数估算成本。每次请求前计算最坏情况下的预算占用，预计下一次请求可能突破总预算或阶段预算时停止派发。价格与汇率是可配置运行参数，并记录在 manifest 中，不能永久硬编码为事实。实际账单可能与估算略有差异，因此还要保留安全余量。

提供 `--dry-run` 查看批次、请求数量和估算上限而不调用 API；提供 `--max-cny 20` 覆盖默认上限。相同模型、提示词版本和输入内容命中缓存时不重复计费。

## 失败、恢复与一致性

- API 限流或服务端错误使用有上限的指数退避，并遵守预算预留；
- 响应无法通过 JSON Schema 时只允许一次定向修复，仍失败则记录并跳过；
- Key 缺失、预算不足、语料版本不一致或输出目录不可写时快速失败；
- 每个批次完成后写入检查点，进程中断后可从未完成阶段恢复；
- 发布文件先写入临时目标并完成全量校验，再原子替换当前候选文件；
- 任一候选缺少原文证据、完整读音或审核状态时不得进入发布文件；
- 构建失败时保留上一次可用候选库，不发布半成品。

## 测试策略

默认测试全部使用固定语料夹具和模型模拟响应，不访问网络、不产生费用。测试范围包括：

- JSON Schema 和模型响应解析；
- 古籍原句及取字位置回查；
- 规范字、负面语境、多音字、谐音和去重规则；
- 分角色审查状态机以及硬规则不可被高分覆盖；
- 缓存命中、断点恢复、限流重试和无效 JSON；
- 阶段预算与 20 元总预算边界；
- 发布文件的完整性、稳定 ID 和旧反馈迁移；
- 网页加载、个性推荐、MMR、收藏、搜索和 GitHub Pages 构建。

另提供显式执行、最高 1 元预算的真实 API 冒烟测试，用于验证鉴权、模型名称和结构化输出。它不属于默认 CI，也不允许使用已经暴露的 Key。

## 验收标准

- 第一轮产出约 300–500 个完整通过审核的候选；数量不足时报告原因，不降低硬门槛凑数。
- 人工随机抽查 50 个高分名字，至少 80% 没有明显难听、随机拼字、语义残缺或出处失实问题。
- 同一批抽查中，至少 40% 值得用户进入认真比较范围。
- 发布候选的原句、书目、篇章和取字位置均可由本地语料复核。
- 候选池不会被“玉、影、清、月”等少数字或单一典籍主导。
- 工厂可在中断后续跑，缓存请求不重复收费，估算费用不突破配置的 20 元上限。
- Key 不出现在 Git 历史、构建产物、报告、缓存键、网页资源和测试快照中。
- 全部单元测试、类型检查、生产构建以及桌面和移动端关键流程验证通过。

若人工抽查未达到质量门槛，先调整检索、提示词或审核规则并使用小批次复测，不使用剩余预算盲目扩量。
