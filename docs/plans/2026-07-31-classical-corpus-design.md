# 核心古籍全文库与静态检索设计

日期：2026-07-31

## 目标

为“女孩取名实验室”建立第一版可审计的核心古籍全文库，使用户输入任意两个名用字时，系统在古籍全文而非既有候选片段中检索原句。第一版收录 50–100 部取名相关核心典籍，继续部署在 GitHub Pages，不依赖运行时服务器。

本设计不宣称覆盖全部传世古籍。页面必须公开书目、版本、数据来源与构建时间；无命中只能解释为“当前收录语料未命中”。

## 范围

第一批优先覆盖：

- 《诗经》《楚辞》；
- 四书、《周易》《礼记》等经部核心文本；
- 《老子》《庄子》《荀子》等先秦诸子；
- 适合取名语境的汉魏辞赋、六朝诗文；
- 经授权核验后纳入的唐宋诗文核心选集。

不在第一版范围内：大型丛书全集、地方志、佛道藏全文、现代译注、在线语义模型，以及需要后端数据库的模糊语义搜索。

## 数据治理

每部书在清单中记录：

- 稳定书籍编号、规范书名、篇章层级；
- 底本或电子版本说明；
- 数据来源网址、授权或公版状态；
- 繁简与标点处理方式；
- 校验状态和最后构建时间。

来源、版本或授权不清的数据不得进入正式构建。原始数据和生成产物分离，生成文件不得手工维护。

## 统一语料格式

标准化后的最小单位是原句：

```ts
interface CorpusPassage {
  id: string;
  bookId: string;
  workId: string;
  chapterId: string;
  workTitle: string;
  chapterTitle: string;
  order: number;
  text: string;
  normalizedText: string;
  sourceUrl: string;
  verificationUrl: string;
}
```

`text` 保留上游转录中的繁简与展示标点；`normalizedText` 仅用于检索，通过固定版本 OpenCC 转为简体后去除标点和非汉字字符。篇章、作品和书籍使用独立编号，避免从书名字符串猜测层级。繁体查询字通过独立别名表映射到同一检索索引，不改写展示原文。

## 静态构建产物

构建脚本从经过审核的源文件生成：

- `catalog.json`：完整书目、覆盖范围、版本与统计；
- `index/<bucket>-<part>.json`：每个汉字对应的紧凑数字编号、正文分片编号和字内位置；
- `texts/<book-id>/<part>.json`：按书与体积分片的原句与元数据；
- `aliases.json`：正文中实际出现过的繁简字符别名；
- `build-report.json`：重复编号、空句、无来源、异常字符和体积报告。

索引文件名使用 Unicode 代码点的高字节分桶，而不是直接使用汉字。高频字可拆成多片，低频字合并到同一静态文件；这既避免路径兼容问题，也不会产生几万个冷僻字小文件。分片目标约 700 KiB，构建门禁要求每个生成文件不超过 1 MiB。

## 浏览器查询流程

1. 用户输入姓名后，加载轻量书目和繁简别名表，规范化出一至两个名用字。
2. 根据目录中的有效桶清单按需下载相关字符索引，缺桶按“未收录该字”处理。
3. 在浏览器中求原句交集、同篇关系、同书关系与跨书组合，并限制各等级展示数量。
4. 只下载入选证据所需的书籍文本分片，渲染原句、固定机器来源和独立公版核验链接。
5. 请求 Promise 按构建版本在当前页面会话内复用；分片失败返回明确错误，不返回假阴性。

当前 70 部语料仍不在浏览器一次性加载；查询只读取一至两个字索引和入选原句所在的正文分片，因此暂不引入 Web Worker 或 IndexedDB。后续根据真实终端耗时决定是否启用。

索引或文本分片加载失败时，页面显示可重试状态，不得把网络失败展示成“没有典故”。

## A–F 证据分级

- A：两个字按名字顺序在有可靠展示标点的转录中直接相连；这仍只是字符关系，须根据句义判断是否成词。
- B：两个字在同一原句或机器检索段中隔字、首尾、反序出现；无可靠句读来源中的相邻字也保守归入 B。
- C：两个字出现在同一作品或篇章的不同原句中。
- D：两个字出现在同一部书的不同篇章中。
- E：两个字分别来自不同典籍，只构成跨典命名组合。
- F：只检索到单字古典用例，不构成完整名字出处。

A–C 可以称为共同文本关系；D–E 必须提示“不是原文固有词组”；F 必须提示“不能作为完整名字出处”。训诂证据须来自《说文》《尔雅》等专门字书数据，不得用普通用例冒充。

## 前端组件

- 覆盖清单：显示书目、版本、状态和原句数量。
- 名字检索器：管理输入、查询状态和缓存状态。
- 检索 Worker：执行索引求交、分级和排序。
- 证据结果组：按 A–F 展示并保留逐条核验链接。
- 语料状态提示：区分未命中、未收录、加载失败和索引损坏。

现有 126 条人工片段保留为回归样本和人工精选层，不再作为全文反查的唯一数据源。

## 测试与验收

构建测试：

- 所有书、篇、句编号唯一；
- 每条原句可回溯到书目和来源；
- 字符索引位置能还原原句；
- 生成结果可重复，构建报告无阻断错误；
- 每个静态分片满足体积预算。

查询测试：

- A–F 每一级都有固定样例；
- 繁简、标点、姓氏和单字输入行为明确；
- 网络失败不会返回假阴性；
- 查询排序稳定，不把低等级包装成高等级。

界面验收：

- 桌面和手机无横向溢出；
- 首屏不下载完整语料；
- 输入后只请求相关索引和命中文本；
- GitHub Pages 生产构建可用，刷新子路径不会丢失应用状态。

## 分阶段交付

1. 建立书目清单、统一格式和构建报告。
2. 用少量公版全文打通分片索引与查询 Worker。
3. 将核心书目扩充至 50–100 部并完成来源核验。
4. 接入覆盖清单、缓存和完整错误状态。
5. 完成体积、性能、移动端和 GitHub Pages 验收。
