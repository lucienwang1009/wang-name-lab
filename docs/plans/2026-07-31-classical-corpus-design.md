# 核心古籍全文库与静态检索设计

日期：2026-07-31

## 目标

为“女孩取名实验室”建立第一版可审计的核心古籍全文库，使用户输入任意两个名用字时，系统在古籍全文而非既有候选片段中检索原句。第一版收录 50–100 部取名相关核心典籍，继续部署在 GitHub Pages，不依赖运行时服务器。

本设计不宣称覆盖全部传世古籍。页面必须公开书目、版本、数据来源与构建时间；无命中只能解释为“当前收录语料未命中”。

## 范围

第一批优先覆盖：

- 《诗经》《楚辞》；
- 四书、《周易》《礼记》等经部核心文本；
- 《老子》《庄子》《荀子》等先秦诸子；
- 适合取名语境的汉魏辞赋、六朝诗文；
- 经授权核验后纳入的唐宋诗文核心选集。

不在第一版范围内：大型丛书全集、地方志、佛道藏全文、现代译注、在线语义模型，以及需要后端数据库的模糊语义搜索。

## 数据治理

每部书在清单中记录：

- 稳定书籍编号、规范书名、篇章层级；
- 底本或电子版本说明；
- 数据来源网址、授权或公版状态；
- 繁简与标点处理方式；
- 校验状态和最后构建时间。

来源、版本或授权不清的数据不得进入正式构建。原始数据和生成产物分离，生成文件不得手工维护。

## 统一语料格式

标准化后的最小单位是原句：

```ts
interface CorpusPassage {
  id: string;
  bookId: string;
  workId: string;
  chapterId: string;
  order: number;
  text: string;
  normalizedText: string;
  sourceUrl: string;
}
```

`text` 保留用于展示的原文，`normalizedText` 仅用于检索，去除标点和非正文空白，但不擅自改字。篇章、作品和书籍必须使用独立编号，避免从书名字符串猜测层级。

## 静态构建产物

构建脚本从经过审核的源文件生成：

- `catalog.json`：完整书目、覆盖范围、版本与统计；
- `index/<codepoint>.json`：每个汉字对应的原句编号和字内位置；
- `texts/<book-id>.json`：按书分片的原句与元数据；
- `build-report.json`：重复编号、空句、无来源、异常字符和体积报告。

文件名使用 Unicode 码点而不是直接使用汉字，避免静态托管路径兼容问题。任何单个生成文件都必须远小于 GitHub 的 100 MiB 单文件限制。

## 浏览器查询流程

1. 首页只加载轻量书目和当前覆盖统计。
2. 用户输入姓名后，规范化出一至两个名用字。
3. 按需下载对应字符索引；结果在浏览器缓存。
4. 在 Web Worker 中求交集、同篇关系与跨书组合。
5. 只下载命中书籍的文本分片，渲染原句和核验链接。
6. 将书目、索引和文本分片缓存在 IndexedDB，并根据构建版本失效。

索引或文本分片加载失败时，页面显示可重试状态，不得把网络失败展示成“没有典故”。

## A–F 证据分级

- A：两个字按名字顺序在规范化原文中连续出现。
- B：两个字在同一原句中隔字、首尾或反序出现。
- C：两个字出现在同一作品或篇章的不同原句中。
- D：两个字出现在同一部书的不同篇章中。
- E：两个字分别来自不同典籍，只构成跨典命名组合。
- F：只检索到单字古典用例，不构成完整名字出处。

A–C 可以称为共同文本关系；D–E 必须提示“不是原文固有词组”；F 必须提示“不能作为完整名字出处”。训诂证据须来自《说文》《尔雅》等专门字书数据，不得用普通用例冒充。

## 前端组件

- 覆盖清单：显示书目、版本、状态和原句数量。
- 名字检索器：管理输入、查询状态和缓存状态。
- 检索 Worker：执行索引求交、分级和排序。
- 证据结果组：按 A–F 展示并保留逐条核验链接。
- 语料状态提示：区分未命中、未收录、加载失败和索引损坏。

现有 126 条人工片段保留为回归样本和人工精选层，不再作为全文反查的唯一数据源。

## 测试与验收

构建测试：

- 所有书、篇、句编号唯一；
- 每条原句可回溯到书目和来源；
- 字符索引位置能还原原句；
- 生成结果可重复，构建报告无阻断错误；
- 每个静态分片满足体积预算。

查询测试：

- A–F 每一级都有固定样例；
- 繁简、标点、姓氏和单字输入行为明确；
- 网络失败不会返回假阴性；
- 查询排序稳定，不把低等级包装成高等级。

界面验收：

- 桌面和手机无横向溢出；
- 首屏不下载完整语料；
- 输入后只请求相关索引和命中文本；
- GitHub Pages 生产构建可用，刷新子路径不会丢失应用状态。

## 分阶段交付

1. 建立书目清单、统一格式和构建报告。
2. 用少量公版全文打通分片索引与查询 Worker。
3. 将核心书目扩充至 50–100 部并完成来源核验。
4. 接入覆盖清单、缓存和完整错误状态。
5. 完成体积、性能、移动端和 GitHub Pages 验收。

- 目标书目共 70 部，处于 50–100 部的约定范围内；
